# Baros: отчёты и фонд «Двойка»

Java 21, Spring Boot, Maven. В репозитории два режима запуска:

- обычный: существующий Telegram-бот отчётов (`docker-compose.yaml`);
- профиль `dvoyka`: отдельный Telegram-бот фонда (`docker-compose.dvoyka.yaml`).

У каждого бота свой Telegram-токен и свой процесс. Для «Двойки» не нужен отдельный сервер базы данных: SQLite хранится в `data-dvoyka/dvoyka.sqlite` на VPS. В режиме «Двойки» бот отчётов и его рассылка не запускаются.

## Как устроен остаток

**Остаток = начальная сумма + учтённая «Порча» ESUPL + ручные поступления − расходы.**

Начальную сумму задают один раз после запуска. Дата в `/opening` — начало барного дня в 03:00 по Минску. Начальная сумма должна отражать остаток **до** этого момента. Все поступления ESUPL с этой даты будут добавляться отдельно: не включайте их повторно в начальную сумму.

Например, `/opening 1000 07.10.2026` означает 1000 BYN перед сменой 7 октября. Чеки до 07.10.2026 03:00 не импортируются, поступления следующей смены попадут в фонд после её окончания. Если задаёте остаток в середине смены, возьмите сумму до начала смены, а уже совершённые в ней ручные операции внесите отдельно.

Синхронизация:

- ежедневно в **08:05 Europe/Minsk**, а также по `/sync` или кнопке;
- импортирует скидку `Порча` из `total_discounts` только у чеков с `is_paid=true` и `is_deleted=false`;
- рассматривает завершённые барные дни с даты отсчёта по вчерашний барный день включительно; текущая смена ещё не учитывается;
- перепроверяет весь этот период, чтобы учесть исправления, удаление чеков и позднее закрытие;
- идентифицирует чеки по ESUPL ID и записывает только разницу с предыдущим импортом;
- при удалении/исчезновении ранее импортированного чека или снятии оплаты создаёт отрицательную корректировку;
- сохраняет всю сверку одной транзакцией после успешного получения всех страниц всех дней; при ошибке чтения ничего из неполного результата не записывает;
- никогда не изменяет начальную сумму и ручные операции.

«Остаток» показывает время последней успешной сверки и последний учтённый барный день. При долгом периоде первая и повторные сверки могут занимать время: данные запрашиваются отдельно за каждый день. Автосверка обновляет журнал без рассылки сообщений.

Все операции содержат время, сумму, пояснение, имя и Telegram ID автора. Автоматическая сверка отмечается как `ESUPL · автоматически` (ID 0), ручная — именем инициатора. Суммы хранятся в целых копейках. Повторная доставка одной Telegram-команды не создаёт повторный расход или приход даже после перезапуска.

## Команды

| Команда | Действие |
| --- | --- |
| `/id` | Узнать ID пользователя и чата; работает до настройки доступа |
| `/opening 1000 07.10.2026` | Однократно установить начальный остаток и дату отсчёта |
| `/balance` | Остаток и состояние синхронизации |
| `/add 50 Возврат подотчёта` | Поступление с обязательным пояснением |
| `/spend 25,50 Закупка лимонов` | Расход с обязательным пояснением |
| `+ 50 Возврат подотчёта` | Короткая форма поступления |
| `- 25,50 Закупка лимонов` | Короткая форма расхода |
| `/history` | Последние 10 операций с авторами |
| `/sync` | Сверить завершённые смены с ESUPL |
| `/help` | Подсказка |

Кнопки «Поступление» и «Расход» показывают образец команды. В группах отправляйте slash-команды (`/add`, `/spend`): Telegram privacy mode может не передавать боту обычный текст и нажатия текстовых кнопок. При нескольких ботах используйте `/add@имя_бота`.

Сумма расхода/поступления — положительное число, не больше двух знаков после запятой; пояснение — до 140 символов. Начальный остаток может быть нулевым или отрицательным. Повторно задать его нельзя. Ошибки исправляются обратной операцией с пояснением, чтобы история сохранилась. Расход может сделать остаток отрицательным: фактическую операцию бот не скрывает.

## Запуск второго бота на VPS

Для тестового токена сначала используйте раздел [Тестовый бот](#тестовый-бот): он запускается с отдельной базой и отключённой автосверкой.

1. Создайте отдельного бота через BotFather и получите **его собственный токен**. Не используйте токен действующего бота отчётов.
2. В каталоге проекта создайте отдельный файл настроек:

   ```bash
   cp .env.dvoyka.example .env.dvoyka
   chmod 600 .env.dvoyka
   nano .env.dvoyka
   ```

   Заполните `ESUPL_API_TOKEN` и `DVOYKA_BOT_TOKEN`. Начальный остаток в файл не записывается.

3. Запустите только новый сервис:

   ```bash
   docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml up -d --build
   docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml logs --tail=100
   ```

4. Отправьте `/id` новому боту в личном или общем чате. Добавьте ID сотрудников и инвесторов через запятую в `DVOYKA_ALLOWED_USER_IDS` для личного доступа. Либо добавьте ID рабочей группы в `DVOYKA_ALLOWED_CHAT_IDS`: тогда все её участники смогут смотреть и изменять фонд. Авторство анонимных администраторов и сообщения от имени каналов не принимаются. Личный доступ разрешённого пользователя не даёт доступ посторонней группе.

   Если оба списка пусты, финансовые операции и просмотр фонда закрыты, но `/id` доступна. Бот отчётов сохраняет прежнюю политику доступа.

5. Повторите `up -d` из шага 3 после изменения настроек. Затем в разрешённом чате задайте `/opening`, выполните `/sync` и проверьте `/balance`. Если дата отсчёта сегодня, первый импорт станет доступен после завершения барного дня в 03:00.

При обновлении используйте те же команды `up -d --build`; база остаётся в папке на VPS. Не удаляйте `data-dvoyka`. Не запускайте два процесса с одним токеном или одну базу для разных Telegram-ботов.

Для отключения автоматической сверки задайте `DVOYKA_SYNC_CRON="-"`. Ручная `/sync` останется доступна.

### Резервная копия

SQLite использует WAL. Для простой согласованной копии остановите только «Двойку», скопируйте **всю** папку `data-dvoyka`, затем снова запустите сервис. Копирование одного `.sqlite` во время работы может не сохранить последние операции.

```bash
docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml stop dvoyka-bot
cp -a data-dvoyka "data-dvoyka-backup-$(date +%Y%m%d-%H%M%S)"
docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml start dvoyka-bot
```

После восстановления старой копии могут отсутствовать ручные операции, сделанные после её создания. Их нужно сверить отдельно: ESUPL восстановит только свои поступления.

## Проверка перед рабочим запуском

### Тестовый бот

Тестовый Compose запускает отдельный сервис `dvoyka-test` с отдельной базой в `data-dvoyka-test`. Автосинхронизация всегда выключена; ESUPL вызывается только при ручной `/sync`. Для первых проверок поступлений и расходов ESUPL-токен можно оставить пустым.

В отдельной копии проекта на VPS:

```bash
cp .env.dvoyka-test.example .env.dvoyka-test
chmod 600 .env.dvoyka-test
nano .env.dvoyka-test
```

Вставьте тестовый токен в `DVOYKA_BOT_TOKEN`, сохраните файл и запустите:

```bash
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml up -d --build
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml logs --tail=50
```

1. Отправьте `/id` тестовому боту в личном чате. Впишите **ID пользователя** из ответа в `DVOYKA_ALLOWED_USER_IDS` в `.env.dvoyka-test` и повторите команду `up -d` (без `--build`).
2. Отправьте `/start`. Для тестового остатка задайте `/opening 1000 ДД.ММ.ГГГГ`, заменив дату на **вчерашний барный день**. Это фиктивные деньги только в тестовой базе; ESUPL не изменяется.
3. `/add 50 Тестовое поступление`, затем `/spend 25,50 Тестовый расход`. `/balance` должна показать **1024,50 BYN**. В `/history` должны быть видны обе операции и ваш автор.
4. Перезапустите сервис командой `docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml restart dvoyka-test`. Остаток должен сохраниться. Повторная `/opening` должна быть отклонена.
5. Для проверки интеграции добавьте действующий ESUPL-токен в `.env.dvoyka-test` и повторите `up -d`. Выполните `/sync`, сравните добавленную сумму с «Порчей» за выбранный завершённый барный день. Повторная `/sync` при неизменных чеках должна показать **0 изменений**, остаток не должен увеличиться снова.

Суммы из тестовой базы не переносятся в рабочую автоматически. Для рабочего бота используются его собственный токен, файл `.env.dvoyka` и `docker-compose.dvoyka.yaml`. Остановка тестового сервиса:

```bash
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml stop dvoyka-test
```

### Автоматические проверки

`./mvnw test` на Java 21 проверяет сохранение начальной суммы, повторные команды и сверки, корректировки чеков, откат при сбое, доступ, авторство и оба режима Spring Boot. В Windows используйте `mvnw.cmd test`.

Тесты используют временные базы, заглушку ESUPL и пустые Telegram-токены. Проверка настоящего ESUPL и Telegram требует отдельных тестовых настроек. Перед заполнением рабочего фонда сверьте на тестовой базе один завершённый день, в том числе чек со 100% «Порчей»: проверьте, что ESUPL помечает его `is_paid=true`, возвращает `total_discounts` и корректную временную зону `event_date`. Неполные ответы блокируют импорт. Данные об открытых неоплаченных чеках в фонд не попадают.
