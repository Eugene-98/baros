# Baros: отчёты и фонд «Двойка»

Java 21, Spring Boot, Maven. В репозитории два режима запуска:

- обычный: существующий Telegram-бот отчётов (`docker-compose.yaml`);
- профиль `dvoyka`: отдельный Telegram-бот фонда (`docker-compose.dvoyka.yaml`), барный день 08:00–08:00 по Минску.

Бот отчётов в обычном режиме сохраняет прежнюю границу 03:00 и рассылку в 08:00.

У каждого бота свой Telegram-токен и свой процесс. Для «Двойки» не нужен отдельный сервер базы данных: SQLite хранится в `data-dvoyka/dvoyka.sqlite` на VPS. В режиме «Двойки» бот отчётов и его рассылка не запускаются.

## Как устроен остаток

**Остаток = начальная сумма + учтённая «Порча» ESUPL + ручные поступления − расходы.**

Начальную сумму задают один раз после запуска. Для новой базы дата в `/opening` — начало барного дня в 08:00 по Минску. Начальная сумма должна отражать остаток **до** этого момента. Все поступления ESUPL с этой даты будут добавляться отдельно: не включайте их повторно в начальную сумму.

Например, `/opening 1000 07.10.2026` означает 1000 BYN перед сменой 7 октября. Чеки до 07.10.2026 08:00 не импортируются, поступления следующей смены попадут в фонд после её окончания. Если задаёте остаток в середине смены, возьмите сумму до начала смены, а уже совершённые в ней ручные операции внесите отдельно.

Синхронизация:

- автоматически ежедневно в **08:05 Europe/Minsk** и при запуске приложения, чтобы догрузить пропущенные завершённые дни; кнопки ручной синхронизации нет;
- импортирует скидку `Порча` из `total_discounts` только у чеков с `is_paid=true` и `is_deleted=false`;
- рассматривает завершённые барные дни с даты отсчёта по вчерашний барный день включительно; текущая смена ещё не учитывается;
- запрашивает полные календарные даты с запасом для UTC и времени бара, читает все страницы, затем точно отбирает чеки по `event_date` в интервале от 08:00 включительно до следующих 08:00 исключительно по Минску; соседние чеки из расширенной выборки не блокируют сверку и не зачисляются раньше срока;
- перепроверяет весь этот период, чтобы учесть исправления, удаление чеков и позднее закрытие;
- идентифицирует чеки по ESUPL ID и записывает только разницу с предыдущим импортом;
- при удалении/исчезновении ранее импортированного чека или снятии оплаты создаёт отрицательную корректировку;
- сохраняет всю сверку одной транзакцией после успешного получения всех страниц всех дней; при ошибке чтения ничего из неполного результата не записывает;
- никогда не изменяет начальную сумму и ручные операции.

«Остаток» показывает время последней успешной сверки и последний учтённый барный день. При долгом периоде первая и повторные сверки могут занимать время: данные запрашиваются отдельно за каждый день. Автосверка обновляет журнал без рассылки сообщений.

Например, `event_date=2026-10-23T00:08:33Z` — это 23 октября 03:08:33 по Минску. Теперь такой чек относится к барному дню 22 октября и попадает в автоматическую сверку 23 октября в 08:05. Чек ровно в 08:00 относится уже к следующему барному дню. Время берётся из `event_date` ESUPL. Расширенные запросы могут пересекаться, но точный отбор относит каждый чек только к одному барному дню.

При сбое автоматической сверки код причины попадает в журнал сервера, а время последней успешной сверки в «Остатке» не обновляется. Служебная команда `/sync` сохранена для диагностики и показывает код причины в ответе. Например, `ESUPL_DATE_RANGE` содержит ID чека, `event_date`, время в Минске и запрошенный период; `ESUPL_DISCOUNTS_MISSING` означает отсутствие списка скидок; `ESUPL_HTTP_401` — отказ API в авторизации; `ESUPL_TIMEOUT` — истечение времени ожидания. Сообщение можно передать разработчику без токенов и полного ответа API. До успешного чтения и проверки всех дней частичный импорт не записывается.

При обновлении существующей базы сохраняется исходная граница начального остатка: у старых баз это 03:00. Первый интервал сверки начинается с этой точки и заканчивается на следующих 08:00, последующие интервалы — 08:00–08:00. Благодаря этому первые часы ранее начатого учёта не теряются; уже импортированные чеки распознаются по ID и не зачисляются повторно. Для новых баз час начального остатка сохраняется при `/opening`. Старые открытые страницы истории после изменения границы нужно открыть заново.

В журнале сохраняются время, сумма, пояснение, имя и Telegram ID автора. Автоматическая сверка отмечается как `ESUPL · автоматически` (ID 0), ручная — именем инициатора. В истории показываются дата без времени и имя с ником без Telegram ID. Суммы хранятся в целых копейках. Повторная доставка одной Telegram-команды не создаёт повторный расход или приход даже после перезапуска.

## Команды

| Команда | Действие |
| --- | --- |
| `/id` | Узнать ID пользователя и чата; работает до настройки доступа |
| `/request` | Подать заявку на личный доступ |
| `/staff` | Заявки, роли и отключение доступа; только владелец, в личном диалоге |
| `/categories` | Категории и правила шаблонов; владелец или управляющий, в личном диалоге |
| `/category 28` | Выбрать категорию расхода №28; сотруднику доступны только свои расходы |
| `/opening 1000 07.10.2026` | Однократно установить начальный остаток и дату отсчёта; только владелец |
| `/balance` | Остаток и состояние синхронизации |
| `/add 50 Возврат подотчёта` | Поступление с обязательным пояснением |
| `/spend 25,50 Закупка лимонов` | Расход с обязательным пояснением |
| `+50 Возврат подотчёта` | Короткая форма поступления; пробел после плюса необязателен |
| `-25,50 Закупка лимонов` | Короткая форма расхода; пробел после минуса необязателен |
| `/cancel` | Отменить текущий ввод |
| `/history` | Выбрать историю за сегодня, текущую неделю или текущий месяц |
| `/history today` | История за текущий барный день |
| `/history week` | История с начала текущей недели |
| `/history month` | История с начала текущего месяца |
| `/sync` | Служебная ручная сверка для диагностики; в меню и пользовательской подсказке не показывается |
| `/help` | Подсказка |

Кнопка **«📒 История»** открывает выбор: **«За сегодня»**, **«На текущей неделе»**, **«За месяц»**. День начинается в 08:00 по Минску, неделя — в понедельник в 08:00, месяц — первого числа в 08:00. До 08:00 продолжается предыдущий барный день; в начале недели или месяца это может быть предыдущая неделя или месяц.

История содержит все записи выбранного периода, включая начальный остаток, ручные операции и корректировки ESUPL. Каждая запись занимает три строки: `#номер · дата сумма`, назначение, имя и ник автора. Поступления ESUPL подписываются **«Закрытый чек»**, отрицательные корректировки — **«Корректировка закрытого чека»**; для расходов и ручных поступлений сохраняется введённое пояснение. Время, Telegram ID автора, номер и дата исходного чека ESUPL сохраняются в базе, но не выводятся в истории. У расходов рядом с назначением показывается категория. Сотрудник видит только свои ручные поступления и расходы; владелец и управляющий — полный журнал. Период определяется по **времени записи в журнал**: поступление ESUPL появляется в день сверки. История не запускает синхронизацию автоматически.

Список отображается от новых записей к старым, по семь операций на странице. Кнопки **«Назад»** и **«Вперёд»** позволяют просмотреть весь период. При выборе периода фиксируется набор записей, поэтому новые операции сотрудников не сдвигают страницы. Чтобы обновить список, выберите период повторно. Период и страница сохраняются после перезапуска отдельно для каждого пользователя в каждом чате. Кнопка **«Главное меню»** завершает просмотр. Открытие истории отменяет незавершённый ввод расхода или поступления.

Три способа записать расход:

1. Отправить `-20 Назначение`, `-20.00 Назначение` или `-20,00 Назначение`. Вариант `- 20 Назначение` тоже работает.
2. Нажать **«➖ Расход»**, затем отправить сумму и назначение одним сообщением: `20,50 Закупка лимонов`.
3. Нажать **«➖ Расход»**, выбрать **«Хозяюшка»**, **«Рынок»** или **«Бар Закупка»**, затем отправить только сумму: `20,50`. Название шаблона сохранится как назначение.

После отправки корректной суммы операция сразу записывается, бот показывает остаток и возвращает основное меню. Дополнительного подтверждения нет. Для смены шаблона нажмите другой; для произвольного назначения — **«Своё назначение»**. **«❌ Отмена»** или `/cancel` отменяют ввод до записи. Кнопки остатка, истории, синхронизации и помощи также завершают незаполненный ввод. Уже записанные операции отменяются обратной операцией с пояснением.

Кнопка **«➕ Поступление»** ждёт сумму и назначение одним сообщением: `50 Возврат подотчёта`. Команды `/spend` и `/add` без аргументов включают соответствующий ввод. Выбор режима и шаблона сохраняется после перезапуска отдельно для каждого сотрудника в каждом чате. Ошибка в сумме не сбрасывает выбор и ничего не записывает.

Форматы суммы во всех вариантах одинаковые: `20`, `20.00`, `20,00`, `20.5`, `20,5`. Более двух знаков после разделителя, смешанные разделители и текст вместо числа отклоняются без округления и списания.

В группах Telegram privacy mode может не передавать боту обычный текст и нажатия текстовых кнопок. Пока он включён, используйте полные slash-команды (`/add 50 Возврат`, `/spend 20 Закупка`), либо работайте в личном чате с ботом. При нескольких ботах используйте `/add@имя_бота`.

Сумма расхода/поступления — положительное число, не больше двух знаков после запятой; пояснение — до 140 символов. Начальный остаток может быть нулевым или отрицательным. Повторно задать его нельзя. Ошибки исправляются обратной операцией с пояснением, чтобы история сохранилась. Расход может сделать остаток отрицательным: фактическую операцию бот не скрывает.

## Доступ и сотрудники

Владелец один раз задаётся через `DVOYKA_OWNER_USER_IDS` (личный Telegram ID; несколько владельцев — через запятую). После обновления отправьте `/start`, чтобы увидеть новое меню. Назначить владельца кнопкой нельзя. Удаление владельца из настройки отключает его доступ при следующем запуске; поэтому сохраняйте свой ID в этом списке.

| Роль | Права |
| --- | --- |
| Владелец | Все операции, начальный остаток, полный журнал, категории, заявки и роли |
| Управляющий | Ручные операции, полный журнал, категории, служебная сверка; без управления доступом |
| Сотрудник | Ручные операции, общий остаток, своя история и категории своих расходов |

Добавление человека:

1. Сотрудник открывает **личный диалог** с ботом, отправляет `/start` и нажимает **«Запросить доступ»** (либо `/request`). До одобрения остаток и журнал ему недоступны.
2. Владелец получает уведомление и открывает **«👥 Сотрудники» → «Заявки»**. Выбирает человека и нажимает **«Разрешить · Сотрудник»**, **«Разрешить · Управляющий»** или **«Отклонить заявку»**.
3. Пользователь получает уведомление и нажимает `/start` для обновления меню. Права применяются сразу, без перезапуска сервера.
4. В «Сотрудниках» владелец может изменить роль или отключить доступ. Записи бывшего сотрудника и авторство остаются. Незавершённый ввод и открытые страницы истории очищаются; старые кнопки не обходят проверку прав.

Повторная заявка, пока первая ожидает решения, не создаёт повторных уведомлений. После отказа/отключения повторная заявка возможна не ранее часа после предыдущей; сама по себе она доступ не возвращает. Уведомления хранятся в базе и повторяются при временном сбое Telegram; недоступный получатель не блокирует операции сотрудников. Владельцу нужно открыть диалог с ботом, чтобы Telegram разрешил уведомления. При сбое после фактической доставки уведомление может прийти повторно, но решение по заявке повторно не применяется.

**Обновление старой базы:** личные ID из `DVOYKA_ALLOWED_USER_IDS` и положительные ID личных чатов из `DVOYKA_ALLOWED_CHAT_IDS` однократно добавляются как управляющие, если пользователя ещё нет в базе. После обновления проверьте роли и при необходимости понизьте их до «Сотрудник». Удаление ID из старого списка не отзывает уже выданный доступ — используйте «Отключить доступ». Повторный запуск не восстанавливает отключённых сотрудников.

`DVOYKA_ALLOWED_CHAT_IDS` теперь определяет только разрешённые **группы**: каждому участнику дополнительно нужен одобренный личный доступ. Ранее не перечисленные поимённо участники группы должны подать заявки. Разрешение группы не даёт всем её участникам доступ автоматически. Анонимные администраторы и сообщения от имени каналов не принимаются. Личный доступ не разрешает раскрывать журнал в посторонней группе. Управление доступом и категориями выполняется в личном диалоге. Бот отчётов сохраняет прежнюю политику доступа.

## Категории расходов

Быстрый ввод, все форматы чисел и три прежних шаблона сохраняются. Расход сразу влияет на остаток; выбор категории можно выполнить позже. После записи в личном диалоге бот показывает компактную кнопку **«Выбрать категорию»** или **«Изменить категорию»**.

Начальный список: «Алкоголь и напитки», «Продукты и ингредиенты», «Хозтовары и расходники», «Оборудование и ремонт», «Выплаты сотрудникам», «Доставка и транспорт», «Прочее». Владелец и управляющий могут добавлять, переименовывать, архивировать и восстанавливать категории через **«🏷 Категории»**. Название — до 48 символов, до 20 категорий могут быть активны одновременно. Переименование меняет название категории и в старых записях; изменения сохраняются в отдельном журнале аудита.

Категория хранится отдельно от назначения. «Рынок» и «Хозяюшка» остаются назначениями, а категорию для каждого шаблона можно настроить в **«Категории» → «Категории шаблонов»**. При первом обновлении все правила оставлены **без категории**, чтобы не делать предположений о покупках. Например, настройте «Рынок» → «Продукты и ингредиенты», если это соответствует вашему учёту. После этого и шаблонный ввод, и `-20 Рынок` сразу сохранят расход с этой категорией. Совпадение назначения точное; произвольный текст бот не классифицирует по догадке. Правило применяется только к новым записям.

**«🗂 Без категории»** показывает старые и новые нераспределённые расходы с переходом к выбору категории. Сотруднику доступны только свои расходы, управляющему и владельцу — все. Можно открыть конкретный расход командой `/category НОМЕР`, например `/category 28`.

Архивная категория остаётся на уже записанных расходах, но её нельзя выбрать для новой записи. Если правило шаблона ссылается на архивную категорию, новые расходы идут без категории; после восстановления правило снова действует. Изменение категории не меняет сумму, назначение, автора или дату операции. Начальный остаток, ручные поступления и ESUPL не считаются расходами и не получают расходных категорий. Изменения ролей и категорий записываются в аудит с автором и временем; повторная доставка одной команды не применяет изменение дважды.

Обновление базы добавляет таблицы прав и категорий, сохраняя деньги, записи, черновики и исходную границу начального остатка. Перед обновлением сделайте согласованную резервную копию всей папки данных, как описано ниже.

## Запуск второго бота на VPS

Для тестового токена сначала используйте раздел [Тестовый бот](#тестовый-бот): он запускается с отдельной базой и включённой ежедневной автосверкой для параллельного учёта.

1. Создайте отдельного бота через BotFather и получите **его собственный токен**. Не используйте токен действующего бота отчётов.
2. В каталоге проекта создайте отдельный файл настроек:

   ```bash
   cp .env.dvoyka.example .env.dvoyka
   chmod 600 .env.dvoyka
   nano .env.dvoyka
   ```

   Заполните `ESUPL_API_TOKEN` и `DVOYKA_BOT_TOKEN`. Начальный остаток в файл не записывается.

3. Запустите только новый сервис:

   ```bash
   docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml up -d --build
   docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml logs --tail=100
   ```

4. Отправьте `/id` новому боту в личном диалоге. Впишите свой личный Telegram ID в `DVOYKA_OWNER_USER_IDS`. Новых сотрудников после этого одобряйте через «Сотрудники». Для работы в группе дополнительно впишите её ID в `DVOYKA_ALLOWED_CHAT_IDS`; каждому участнику также требуется одобрение владельца. Старый `DVOYKA_ALLOWED_USER_IDS` можно оставить для переноса существующих пользователей как управляющих.

   Пока владелец и пользователи не настроены, финансовые операции и просмотр фонда закрыты, но `/id` доступна.

5. Повторите `up -d` из шага 3 после изменения настроек. Затем в разрешённом чате задайте `/opening` и проверьте `/balance`. Если дата отсчёта сегодня, первый импорт станет доступен после завершения барного дня в 08:00 и будет загружен в 08:05.

При обновлении используйте те же команды `up -d --build`; база остаётся в папке на VPS. Не удаляйте `data-dvoyka`. Не запускайте два процесса с одним токеном или одну базу для разных Telegram-ботов.

Для отключения автоматической сверки задайте `DVOYKA_SYNC_CRON="-"`: отключаются и расписание, и сверка при запуске. Служебная `/sync` останется доступна.

### Резервная копия

SQLite использует WAL. Для простой согласованной копии остановите только «Двойку», скопируйте **всю** папку `data-dvoyka`, затем снова запустите сервис. Копирование одного `.sqlite` во время работы может не сохранить последние операции.

```bash
docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml stop dvoyka-bot
cp -a data-dvoyka "data-dvoyka-backup-$(date +%Y%m%d-%H%M%S)"
docker compose --env-file .env.dvoyka -f docker-compose.dvoyka.yaml start dvoyka-bot
```

После восстановления старой копии могут отсутствовать ручные операции, сделанные после её создания. Их нужно сверить отдельно: ESUPL восстановит только свои поступления.

## Проверка перед рабочим запуском

### Тестовый бот

Тестовый Compose запускает отдельный сервис `dvoyka-test` с отдельной базой в `data-dvoyka-test`. Включены ежедневная сверка в 08:05 и сверка при запуске; требуется действующий ESUPL-токен. Это среда для параллельного сравнения старого учёта и бота, без переноса денег в рабочую базу автоматически.

Для первого запуска в отдельной копии проекта на VPS (существующий `.env.dvoyka-test` не перезаписывайте):

```bash
cp .env.dvoyka-test.example .env.dvoyka-test
chmod 600 .env.dvoyka-test
nano .env.dvoyka-test
```

Заполните `DVOYKA_BOT_TOKEN`, `ESUPL_API_TOKEN` и оставьте `DVOYKA_SYNC_CRON="0 5 8 * * *"`. Сохраните файл и запустите:

```bash
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml up -d --build
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml logs --tail=50
```

1. Отправьте `/id` тестовому боту в личном чате. Впишите свой ID в `DVOYKA_OWNER_USER_IDS` в `.env.dvoyka-test` и повторите `up -d` после изменения настроек. Отправьте `/start`; остальных сотрудников одобряйте через «Сотрудники».
2. Для **новой базы** задайте `/opening СУММА ДД.ММ.ГГГГ`: фактический остаток до 08:00 выбранной даты. Если настройка идёт позже начала смены, внесите уже совершённые ручные операции отдельно. Не включайте в начальный остаток суммы ESUPL, которые будут импортированы с этой даты.
3. Для **уже используемой тестовой базы** не задавайте начальный остаток повторно. После обновления дождитесь сверки при запуске, сравните остаток бота с фактическими деньгами и старым учётом. Если в базе оставались фиктивные суммы и пробные операции, разницу исправьте одним поступлением/расходом с пояснением «Сверка остатка перед параллельным тестом». Само обновление не сбрасывает деньги и записи.
4. Каждое реальное поступление и расход отражайте один раз в старом способе учёта и один раз в боте, с одинаковой суммой и назначением. Поступления «Порча» в боте добавляются автоматически; вручную их повторять не нужно.
5. После 08:05 ежедневно проверьте «Остаток»: время последней успешной сверки и последний завершённый барный день. Чеки, закрытые после фактического закрытия бара, но до 08:00, относятся к предыдущему барному дню. Чеки после 08:00 — к следующему.
6. Сравнивайте три значения на один и тот же момент: фактические деньги, остаток по старому учёту и остаток бота. Для сравнения смен используйте одинаковый период 08:00–08:00. Фиксируйте дату, три остатка и причину каждой разницы; не маскируйте повторное зачисление ручными поправками.
7. Завершайте параллельный тест после нескольких полных смен без необъяснённых расхождений, включая позднее закрытие чеков и перезапуск бота. Перед переходом на единственный способ учёта сделайте резервную копию всей базы и зафиксируйте согласованный остаток на момент перехода.

После успешного параллельного теста можно продолжить работу в этом же боте и с этой же базой. Если нужен отдельный рабочий бот, суммы и история не переносятся автоматически: он использует собственный токен, файл `.env.dvoyka` и `docker-compose.dvoyka.yaml`. Остановка тестового сервиса:

```bash
docker compose --env-file .env.dvoyka-test -f docker-compose.dvoyka-test.yaml stop dvoyka-test
```

### Автоматические проверки

`./mvnw test` на Java 21 проверяет сохранение начальной суммы, повторные команды и сверки, корректировки чеков, откат при сбое, роли и отзыв доступа (включая старые кнопки и группы), категории и правила шаблонов, миграцию старой базы, авторство, повторную доставку сообщений/нажатий, формат Telegram API и оба режима Spring Boot. В Windows используйте `mvnw.cmd test`.

Тесты используют временные базы, заглушку ESUPL и пустые Telegram-токены. Проверка настоящего ESUPL и Telegram требует отдельных тестовых настроек. Перед заполнением рабочего фонда сверьте на тестовой базе один завершённый день, в том числе чек со 100% «Порчей»: проверьте, что ESUPL помечает его `is_paid=true`, возвращает `total_discounts` и корректную временную зону `event_date`. Неполные ответы блокируют импорт. Данные об открытых неоплаченных чеках в фонд не попадают.
