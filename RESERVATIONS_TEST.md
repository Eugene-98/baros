# «Персонажи» — тестовый бот бронирования v0.1

Один Telegram-бот с меню гостя, сотрудника и владельца. Стек тот же, что у остальных ботов: Java 21, Spring Boot, SQLite, Docker Compose. Отдельный профиль `reservations` запускает только обработчик бронирований. Порт сервера публиковать не нужно.

## Возможности

- Гость: дата из календаря на 30 дней, время с шагом 30 минут, количество гостей, имя, телефон, пожелания; просмотр своих броней и отмена.
- Сотрудник: новые заявки, список на барный день, назначение стола и подтверждение, отклонение, отмена, перенос времени, ручная заявка по телефону или из переписки. После ручного добавления тоже нужно назначить стол и подтвердить.
- Владелец: одобрение запросов `/access`, отзыв доступа через «Сотрудники». Владельцы задаются только в окружении сервиса.
- Уведомления: гостю о решении и переносе, команде — в закрытую группу или сотрудникам в личные чаты. Напоминание гостю за 2 часа; при подтверждении ближе к визиту — в следующем цикле обработки. Для ручной брони Telegram гостя неизвестен, поэтому уведомления получит команда, а с гостем связывается сотрудник.
- История действий сохраняет ID сотрудника. Брони, черновики, права, очередь уведомлений и позиция Telegram сохраняются после перезапуска.

## Границы теста

**Это отдельный тест. Сообщения помечены «Тест · реальный стол не бронируется».** Рабочая Google-таблица «Брони х2» пока не читается и не меняется; текущие реальные брони в бота не перенесены. Проверка пересечений действует только между записями тестового бота. Ссылку пока используйте внутри команды.

Столы по умолчанию: №12 — 5 мест, №13 — 3, №14 — 2, №15 — 3. Red room, «Арка» и «Коктейльный» не настроены: нужна их вместимость и правила объединения. Компания до 20 человек может отправить заявку, но подтверждение возможно только после настройки подходящего стола/зоны. Автоматического объединения столов нет.

Пробные настройки: **18:00–02:00 каждый день, длительность 120 минут**. Это допущение для теста, а не подтверждённый график работы бара. Они меняются в `.env.reservations-test`. Последнее прибытие при этих настройках — 00:00 следующего календарного дня. Например, выбор барного дня 9 ноября и времени 00:00 означает прибытие **10 ноября в 00:00**. В карточках и кнопках указана фактическая дата прибытия; в списках используется барный день. Часовой пояс — `Europe/Minsk`.

Все заявки сначала ожидают решения сотрудника; отправленная заявка не удерживает конкретный стол. При подтверждении выполняется повторная проверка вместимости и пересечений в транзакции SQLite. Следующая бронь может начинаться сразу после окончания предыдущей; буфер на уборку пока не задан. При переносе подтверждённой брони сохраняется её стол; при конфликте исходная бронь остаётся на месте.

## Запуск на существующем VPS

### 1. Создать отдельного бота

В Telegram откройте **@BotFather**, отправьте `/newbot`, задайте название и username. Сохраните токен на сервере в файле окружения. Не используйте токены ботов отчётов и «Двойки» и не публикуйте токен в GitHub.

### 2. Подготовить отдельную папку

Команды выполняются в SSH/Termius на том же VPS. Для них нужны уже установленные Git и Docker Compose.

```bash
git clone --branch feature/reservations-test --single-branch https://github.com/Eugene-98/baros.git ~/baros-reservations-test
cd ~/baros-reservations-test
cp .env.reservations-test.example .env.reservations-test
chmod 600 .env.reservations-test
nano .env.reservations-test
```

Вставьте новый токен после `RESERVATION_BOT_TOKEN=`. На первом запуске `RESERVATION_OWNER_USER_IDS=` можно оставить пустым: бот работает только в режиме настройки и сообщает ID, бронирования отключены.

Перед запуском посмотрите фактическую нагрузку: ресурсы этого VPS из чата не проверены. Лимит нового контейнера — 512 MiB; это ограничение, а не гарантия достаточного запаса на конкретном сервере. Сборка временно потребляет дополнительную память.

```bash
free -h
docker stats --no-stream
docker compose --env-file .env.reservations-test -f docker-compose.reservations-test.yaml up -d --build
docker compose --env-file .env.reservations-test -f docker-compose.reservations-test.yaml logs --tail=60
```

Команды этого Compose управляют только проектом `baros-reservations-test`. База находится в `./data-reservations-test/reservations-test.sqlite`, независимо от папок «Двойки» и отчётов. Запускайте один экземпляр обработчика на один токен и эту базу.

### 3. Назначить владельца

Напишите новому боту `/id` в личном чате. Он сообщит ваш числовой Telegram ID. Внесите его в файл `.env.reservations-test`:

```dotenv
RESERVATION_OWNER_USER_IDS=ВАШ_ЧИСЛОВОЙ_ID
```

Для нескольких владельцев — ID через запятую. Снова выполните:

```bash
docker compose --env-file .env.reservations-test -f docker-compose.reservations-test.yaml up -d
```

Напишите боту `/start`. Появятся меню сотрудника и кнопка «Сотрудники». При пустом списке владельцев заявки недоступны; первый обратившийся пользователь не получает права автоматически.

### 4. Подключить команду

Каждый сотрудник открывает бота, нажимает `/start`, затем отправляет `/access`. Владелец получает личное сообщение с кнопками «Разрешить» и «Отклонить». После одобрения сотрудник снова нажимает `/start`.

Для общих уведомлений создайте **закрытую группу команды**, добавьте туда бота и отправьте `/id@username_вашего_бота`. Внесите отрицательный ID группы в `RESERVATION_STAFF_CHAT_ID` и повторите `up -d`. Сотрудникам не нужны права администратора группы: права на бронирования выдаёт владелец в боте. Нажатия проверяются по Telegram ID даже в группе. При `RESERVATION_STAFF_CHAT_ID=0` уведомления направляются владельцам и одобренным сотрудникам в личные чаты.

В группе доступны подтверждение с выбором стола, отклонение и отмена. Подробный просмотр, ручное добавление и перенос выполняются в личном чате с ботом. При отзыве доступа сотрудника также удалите его из группы, если он больше не должен видеть командные уведомления с контактами гостей.

### 5. Пройти тест

1. С обычного аккаунта отправить заявку; проверить, что она ожидает подтверждения.
2. С аккаунта сотрудника назначить стол, проверить подтверждение у гостя.
3. Сделать пересекающуюся заявку и попытаться назначить тот же стол: бот должен отказать.
4. Перенести бронь и проверить новое время в обеих карточках.
5. Отменить свою бронь с аккаунта гостя; проверить освобождение стола.
6. Внести ручную заявку и подтвердить её.
7. Перезапустить контейнер; проверить сохранность заявок и доступа.

Тестовые записи могут иметь реальные телефоны участников теста; не вводите в тест данные посторонних гостей.

## Обновление и остановка

Из папки `~/baros-reservations-test`:

```bash
git pull --ff-only
docker compose --env-file .env.reservations-test -f docker-compose.reservations-test.yaml up -d --build
```

Остановить только этот тест:

```bash
docker compose --env-file .env.reservations-test -f docker-compose.reservations-test.yaml stop
```

Для согласованной резервной копии остановите этот сервис, скопируйте **всю** папку `data-reservations-test` и снова выполните `up -d`. Не удаляйте папку данных при обновлении.

## Проверки кода

На полноценном JDK 21:

```bash
bash mvnw test
```

Проверены заявки и ручной ввод, контроль доступа в личных чатах/группах, отзыв роли, вместимость, пересечения и соседние интервалы, полночь и закрытие, перенос с сохранением исходной брони при конфликте, повторные обновления и устаревшие кнопки, восстановление после перезапуска, транзакционный откат при сбое, напоминания, HTTP-клиент и повторная доставка уведомлений. Уведомления об устаревшей версии брони пропускаются: отмена не должна сопровождаться запоздавшим подтверждением. Telegram допускает повторную доставку сообщения после сетевого обрыва; состояние бронирования при этом не дублируется.

Сборка Docker и проверка с настоящим Telegram-токеном выполняются на VPS при запуске. В среде разработки Docker и доступ к серверу не предоставлены.

## Следующий этап после теста

Согласовать график работы, длительность визита, вместимость зон и объединение столов. Затем подключить отдельный структурированный журнал к Google Sheets, перенести актуальные брони и сверить заполнение календаря. После этого можно готовить публичный запуск.
